# B2-2 R01 — Evaluation Q&A Reference

실제 평가에서는 본인 팀의 Issue/PR/Review/Conflict 링크를 근거로 설명합니다.

## 1. 왜 branch를 작업 단위로 나누는가?

한 branch에 여러 목적을 섞으면 리뷰 범위와 rollback 범위가 커집니다. Reference는 Issue 하나와 feature branch 하나를 가깝게 연결해 변경 이유와 책임을 추적하기 쉽게 합니다.

## 2. GitHub Flow에서 main을 항상 깨지지 않는 상태로 유지하는 이유는?

main이 팀의 통합 기준점이기 때문입니다. 누구나 main에서 새 작업을 시작하고 필요하면 배포할 수 있어야 협업 병목과 복구 비용이 줄어듭니다.

## 3. 왜 main 직접 push 대신 PR + 승인인가?

PR은 변경 이유, diff, 테스트, 리뷰 대화를 한 곳에 남깁니다. 최소 1명 승인은 작성자 혼자 놓친 오류를 줄이고 책임을 분산하며, 누가 무엇을 왜 병합했는지 추적할 수 있게 합니다.

## 4. Issue와 PR을 연결하는 이유는?

Issue는 문제/작업 이유, PR은 실제 변경을 담습니다. `Closes #n`으로 연결하면 요구사항 → 구현 → 리뷰 → 완료를 추적할 수 있고 merge 시 Issue 자동 종료 같은 GitHub 자동화도 활용할 수 있습니다.

## 5. What/Why/How를 PR에 고정하는 이유는?

- What: diff의 요약
- Why: 변경이 필요한 배경
- How: 검증 방법

세 항목을 고정하면 리뷰어가 코드만 보고 의도를 추측하는 시간을 줄이고 PR 품질을 일정하게 유지합니다.

## 6. LGTM만으로 부족한 이유는?

실질 리뷰의 학습 목표는 작성자가 놓친 위험, 대안, 경계값을 함께 검토하는 것입니다. 특정 파일/라인을 근거로 질문·리스크·대안·테스트 누락 등을 남기고 작성자가 답변/수정해야 협업 기록으로 의미가 있습니다.

## 7. 충돌이 발생하면 어떤 순서로 대응하는가?

`공유 → 양쪽 변경 의도 확인 → 담당자 중심 해결 → 테스트 → PR 업데이트 → conflict-resolution 기록` 순서를 사용합니다. 충돌 마커를 기계적으로 지우기보다 두 변경 목적을 먼저 확인합니다.

## 8. 충돌 마커의 의미는?

- `<<<<<<<`: 현재 branch 쪽 변경 시작
- `=======`: 양쪽 변경 경계
- `>>>>>>>`: 상대 branch 쪽 변경 끝

최종 파일에는 마커가 남아서는 안 되며 어떤 내용을 남길지는 요구사항과 두 변경의 의도를 기준으로 결정합니다.

## 9. 비자명 충돌에서 의사결정 기준은?

같은 hunk 충돌이라면 어느 한쪽을 무조건 선택하지 않고 두 작업의 Issue 목적, 테스트, API/문서 계약을 비교합니다. rename/delete vs modify라면 파일의 최종 존재 위치와 수정 내용의 보존 필요성을 팀이 합의합니다.

## 10. `reset`과 `revert`는 언제 다르게 쓰는가?

`reset --soft`는 아직 공유하지 않은 로컬 commit을 취소하고 변경을 유지할 때 적합합니다. 이미 push되어 다른 사람이 볼 수 있는 commit은 history를 지우기보다 `revert`로 반대 변경을 담은 새 commit을 만드는 것이 안전합니다.

## 11. amend는 언제 안전한가?

아직 push하지 않은 자신의 최근 commit 메시지/내용을 고칠 때 안전합니다. push 후 amend는 SHA를 바꾸므로 다른 사람이 해당 commit을 기반으로 작업했다면 충돌과 history divergence를 만들 수 있습니다.

## 12. stash는 왜 필요한가?

미완성 변경을 commit으로 남기기 싫지만 다른 branch로 이동해야 할 때 임시 보관합니다. `stash pop` 후 conflict 가능성이 있으므로 반드시 `git status`를 확인합니다.

## 13. 트러블슈팅 로그를 재현 가능하게 만드는 고정 항목은?

상황, 재현 조건, 실행 전 상태, 명령, 실행 후 결과, 명령 선택 이유, 주의점, 참여자, Issue/PR/Commit 링크를 남깁니다. 다른 팀원이 같은 상황에서 절차를 따라갈 수 있어야 합니다.

## 14. main에 긴급 hotfix가 필요하면?

main에서 최신 상태를 받고 `feature/hotfix-*` 또는 팀 규칙의 짧은 작업 branch를 만들고 수정 → 테스트 → PR → 긴급 리뷰/승인 → merge 순서를 유지합니다. 긴급하다는 이유로 main 직접 push를 기본 경로로 만들지 않습니다.

## 15. 이미 의미 없는 commit 메시지를 여러 개 push했다면?

공유 history를 무리하게 rewrite하지 않습니다. 현재 PR이 열려 있다면 이후 commit과 PR 설명에서 변경 의도를 명확히 보완하고, 팀이 merge 전략(squash 등)을 합의할 수 있습니다. 이미 main에 병합된 history를 임의 force-push로 다시 쓰지 않습니다.

## 16. 같은 파일에서 충돌이 반복되면 어떻게 예방하는가?

작업 경계를 더 작게 나누고 ownership/담당 영역을 조정하며, 같은 파일의 같은 영역을 동시에 수정하기 전에 Issue/팀 채널에서 조율합니다. 큰 공용 파일을 역할별 모듈로 분리하는 것도 예방 방법입니다.

## 17. rebase가 깔끔하지만 협업에서 위험한 이유는?

rebase는 commit을 새 부모 위에 다시 만들어 SHA를 바꿉니다. 개인 feature branch 정리에는 유용하지만 shared branch에서 수행하면 다른 사람의 history와 갈라질 수 있습니다. 보너스로 수행할 경우 개인 branch, 팀 합의, force-with-lease 등 안전 수칙이 필요합니다.
